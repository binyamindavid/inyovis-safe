# Direct upload intake

The browser sends small, same-origin session and completion requests through the Next.js gateway. A 25 MiB PDF body would exceed common hosted function request limits, so the bytes go directly to private S3-compatible staging. Go issues a 15-minute POST policy for one server-generated staging key and a `content-length-range` of 1 to the configurable cap (25 MiB by default). An upload session may begin finalisation within 24 hours. Once finalisation starts, it remains eligible for reconciliation beyond that deadline.

The application credentials can read and write the private bucket; the browser receives only the signed POST form. Neither staging nor final originals have public-read grants or download routes. The browser grant may be replayed until expiry. Go hashes a bounded read into an immutable buffer and writes a private `prepared/` object from those verified bytes. It reads and hashes that object back before committing the `finalising` intent. After a process crash, the reconciler can promote the prepared bytes even if the browser replays and changes staging. The final key is deterministic and private. A conditional final PUT prevents overwrite where supported. Go reads the final object back and hashes it before committing the receipt. A conflicting object at that key is an integrity failure.

The database row lock serializes receipt commits for one session. Storage reads and writes run outside the receipt transaction. A shared archive advisory lock serializes final receipt authorisation with membership changes. The receipt transaction creates the stored object, submission, received document, pending job, and audit event and marks the session complete. Reconciliation discovers only stalled archive and session IDs through a dedicated role, then uses the same finaliser in the uploader's archive-scoped RLS context. The audit row retains the uploader and labels the reconciler as system actor. A stalled session with a transient storage or database failure receives a bounded retry backoff, so later candidates still run. Integrity or authorization failures are flagged as orphans and logged by session ID only.

## Provider verification

The code relies on the provider enforcing the POST policy's exact key and content length range, and on the final PUT's `If-None-Match: *`. These are **not assumed to be equivalent across S3-compatible providers**. Against a disposable SeaweedFS 4.53 mini instance, the exact-key POST policy accepted a 5.4 MB PDF, rejected a changed key with 403, and rejected 25 MiB plus one byte with 400. A preflight from `https://localhost:3000` received the matching `Access-Control-Allow-Origin`, and a real browser POST from `https://localhost:3002` succeeded. SeaweedFS honored `If-None-Match: *` for the final PUT; a second write to the same key failed. The final readback matched the browser fixture byte-for-byte, including its embedded XML. An unauthenticated GET of the final object returned 403. The provider returns `403 AccessDenied` for a changed key and `400 EntityTooLarge` for an oversized upload. Production buckets must repeat these checks, configure CORS for their actual app origin, and remain private. No public-read operation is exposed.

## Lifecycle requirements

Configure a production bucket lifecycle rule to expire `staging/` objects after 48 hours; the database allows only 24 hours to start finalisation. Do **not** apply that rule to `prepared/`: a `finalising` session needs its verified recovery copy until receipt or explicit orphan resolution. Prepared objects and flagged orphans require an operational cleanup job after receipt or manual reconciliation; this implementation does not yet remove those objects. Originals have no lifecycle expiry here.
